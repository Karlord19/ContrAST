\section{Code clones}

Code clones are similar or identical code fragments that appear in different parts of a codebase.
They can be classified into different types based on their similarity.

\begin{codepair}[Type 1 clones]
\label{prg:type1clones}
\begin{lstlisting}[language=C++]
int add3(int a) {
    // sum of parameter and 3
    return a + 3;
}
\end{lstlisting}
\codepairsep
\begin{lstlisting}[language=C++]
int add3(int a) {
  return a + 3;
}
\end{lstlisting}
\end{codepair}

Type 1 clones are identical code fragments that differ only in whitespace and comments, see Program \ref{prg:type1clones}.

\begin{codepair}[Type 2 clones]
\label{prg:type2clones}
\begin{lstlisting}[language=C++]
int add3(int a) {
    // sum of parameter and 3
    return a + 3;
}
\end{lstlisting}
\codepairsep
\begin{lstlisting}[language=C++]
float add4(float x) {
  return x + 4.0f;
}
\end{lstlisting}
\end{codepair}

Type 2 clones, apart from whitespace and comments, also allow for renaming of identifiers and change in literals and types, see Program \ref{prg:type2clones}.

\begin{codepair}[Type 3 clones]
\label{prg:type3clones}
\begin{lstlisting}[language=C++]
int add3(int a) {
    // sum of parameter and 3
    return a + 3;
}
\end{lstlisting}
\codepairsep
\begin{lstlisting}[language=C++]
float add4(float x) {
  auto result = x + 4.0f;
  return result;
}
\end{lstlisting}
\end{codepair}

Type 3 clones might have some statements added, modified, or removed, but still show a significant similarity in their structure and functionality, see Program \ref{prg:type3clones}.

Type 4 clones are code fragments that perform the same functionality but are implemented differently.
An example of type 4 clones would be two different implementations of a sorting algorithm.

In the context of introductory programming courses, every solution to a given problem would be considered a type 4 clone of every other solution, as they all perform the same functionality.
We need to then focus on detecting type 1 and type 2 clones, and ideally also some level of type 3 clones, as they are more likely to be the result of copying and modifying code, rather than independently solving the same problem.

\section{Clone detection approaches}

From the input, possibly thousands of source files, a clone detector should identify and report all the code clones present in the codebase.
To achieve this, a sequence of steps is typically followed \cite{roy09}.
The detector may use only a subset of these steps, depending on the specific approach and the type of clones it aims to detect.

\begin{enumerate}
\item Preprocessing: Generated files are removed. The remaining files are fractioned into relevant units, such as functions or classes.
\item Transformation: The code is transformed into an intermediate representation.
\item Extraction: One of the following approaches is used to extract features from the code:
  \begin{itemize}
    \item Tokenization: A lexical analysis is performed, and the code is represented as a sequence of tokens.
    \item Parsing: A syntactic analysis is performed, and the code is represented as a parse tree or an abstract syntax tree (AST).
    \item Control and data flow analysis: A semantic analysis is performed, and the code is represented as a program dependence graph (PDG).
  \end{itemize}
\item Normalization: To reduce uninteresting differences between code fragments, whitespace and comments are removed, identifiers are consistently named or replaced with placeholders, and some code constructs are simplified.
\item Match detection: The units are compared and similar ones are yielded as potential clones.
\item Formatting: The original locations of the detected fragments are retrieved.
\item Filtering: Potential clones are filtered either by a human or with a heuristic, to remove false positives and retain only the true clones.
\item Aggregation: If there are many clones similar to each other, they can be grouped together to create a more compact report.
\end{enumerate}

We can then classify clone detection approaches based on the steps they use.
The level of analysis performed then impacts the types of clones that can be detected, as well as the precision and recall of the detector.

\begin{itemize}
\item Textual: The code is treated as plain text, or only some basic parsing is performed.
\item Lexical (token-based): The code is first tokenized and then normalized, and the resulting token sequences are sent for match detection.
\item Syntactic (tree-based): The code is parsed into an AST. Algorithms for tree similarity are then used. The trees can also be serialized into a token or string representation, and then token-based approaches can be applied.
\item Syntactic (metrics-based): The code is parsed into an AST, and then various metrics are computed. The resulting vectors of metrics are then compared using a similarity measure.
\item Semantic: The code is analyzed to extract its semantics. This can be done using program dependence graphs, information retrieval techniques, artificial intelligence, \dots
\end{itemize}

\section{Syntactic analysis of source code}

We can use Flex \cite{flex} and Bison \cite{bison} as a lexer and parser, but it requires us to write a grammar for the language we want to parse.
It is rather difficult to write a complete grammar for a complex language, and it is also difficult to keep it up to date with the language evolution.

Doxygen \cite{doxygenparser} uses Flex to tokenize the code and then builds a simple AST.
It needs to handle documentation blocks, compiler directives, and incomplete code, all under custom settings defined by the user.

Python has a standard library module \cite{pythonast} for inspecting the AST of Python code.
It is used by Saksa \cite{saksa20} for parsing Python code and then hashing the resulting ASTs to find identical code fragments.

Similarly to Python, Java and C\# also have their own standard modules for inspecting the AST of Java \cite{javaast} and C\# \cite{csharpast} code, respectively.
Native support from the official distributions ensures the correctness and up-to-dateness of the modules, and also provides all the information about the code and AST.

Tree-sitter \cite{treesitter} is a parser generator tool (generates parser from a grammar) and an incremental parsing library (it is able to update the parse tree as the code changes).
It provides parsers for many programming languages and has a wide range of bindings for different programming languages for easy integration into various tools \cite{dolos22}.

ANTLR \cite{antlr} is a parser generator tool.
It also generates tree walkers that make it easy to traverse the parse tree.
It provides grammars for many programming languages, but users often create their own grammars for specific data formats, such as query parsing in Twitter search \cite{antlr}.

Clang offers libraries for building tools that analyze and transform C/C++ code.
It provides a powerful API for inspecting and manipulating the AST, and is able to do full semantic analysis of the code.
It provides LibTooling \cite{libtooling} for building standalone tools, LibFormat \cite{libformat} for automatic code formatting, LibASTMatchers \cite{libastmatchers} for searching for specific AST nodes, and much more.

\section{Clone detection tools}

We shortly review some of the existing plagiarism detection tools that accept source code as input, especially those that are relevant to our work or are widely used.
We focus only on the original ideas behind the tools; many of them have evolved and now include various new approaches and features.

Probably the most widely used detector is Moss (Measure of Software Similarity) using the winnowing algorithm \cite{moss03}.
It primarily operates on source code, but the algorithm itself is textual.
The code is first parsed and normalized based on the input format and then printed to a string representation.
We call a substring of the string representation of length $n$ a $n$-gram.
All $n$-grams are collected and hashed, and then all windows of a certain size are created from the sequence of hashes.
From each window, the minimum hash value is selected as a fingerprint.
The fingerprints are then stored, and the detector quickly finds matching fingerprints between different documents.

A tool called sim \cite{sim99} compares two documents at a time.
First, the code is tokenized and normalized.
Then, a string alignment algorithm is applied.
If the aligned tokens are the same, a positive score is given, if they are different, a negative score is given, and if a gap needs to be inserted, a gap penalty is applied.
The final score is based on the best alignment of the two token sequences.

JPlag \cite{jplag02} also accepts two documents at a time and tokenizes them, but uses a string tiling algorithm on the token sequences.
It tries to find the longest common substrings between the two sequences, marks them as clones, and removes them from the sequences.
This process is repeated until no more common substrings of a certain length can be found.
This approach easily detects clones with transposed code segments.

NiCad \cite{nicad08} normalizes the code and pretty-prints it to a string representation.
Then, the fragments are compared line by line, and the longest common subsequences are found.

iClones \cite{iclones09} addresses the problem of needing to run a new analysis on every small change in the codebase, which is very inefficient.
The idea is to build a suffix tree from the tokenized and normalized code, and update the tree locally and incrementally as the code changes.

Dolos \cite{dolos22} creates fingerprints similar to Moss, but operates on normalized token sequences instead. For each pair of documents, similarity, total overlap and longest shared fragment are computed. Based on those metrics, the candidates are ordered and filtered.

BLEU (BiLingual Evaluation Understudy) \cite{bleu02} is a metric originally designed for evaluating machine translation, with the idea that a good machine translation should be similar to a professional human translation. A sequence of words is considered, all $n$-grams are extracted, with an upper limit on $n$. The similarity score is based on the number of matching $n$-grams between two documents.

CodeBLEU \cite{codebleu20} is an adaptation of BLEU for source code. It also considers matching the syntactic AST and the semantic dataflow, in addition to the lexical $n$-grams.

CrystalBLEU \cite{crystalbleu23} differs from BLEU in filtering out completely the most common $n$-grams, as they come from the nature of the language rather that from the specific code fragment.

A tree is a data structure that consists of nodes connected by edges, where each node has a label and zero or more child nodes.
Unweighted tree edit distance, or unweighted TED for short, is a measure of similarity between two trees, $T_1$ and $T_2$.
It is defined as the minimum number of edit operations that transforms $T_1$ into $T_2$.
The edit operations typically include relabeling \ref{fig:ted-rename}, insertion \ref{fig:ted-insert}, and deletion \ref{fig:ted-delete}.
Insertion of a node X under a node Y means that a consecutive subset S of children of Y are reattached to X, and X is then added as a child of Y at the position of S.
Deletion of a node X means that X is removed, and its children are reattached to the parent of X at the position of X.
It can be easily seen that inserting a node into $T_1$ is equivalent to deleting a node from $T_2$, and vice versa.

In a more general setting, we can assign different cost values to each type of edit operation, and different costs to different labels.
Weighted TED is then defined as the minimum weighted number of edit operations that transforms $T_1$ into $T_2$.
By TED we will refer to weighted TED, unless otherwise specified.

The formal definition of TED is as follows \cite{zhang89}:
\begin{defn}[Tree edit distance]
Let $c$ be a distance metric that assigns a non-negative cost to each edit operation based on the labels of the nodes involved in the operation.
If $S$ is a sequence of edit operations, we define $c(S)$ as the sum of the costs of the edit operations in $S$.
Let $T_1$ and $T_2$ be two labeled trees.
The tree edit distance between $T_1$ and $T_2$ is defined as
$$TED(T_1, T_2) = \min \{c(S)\},$$ where $S$ is a sequence of edit operations transforming $T_1$ into $T_2$.
\end{defn}
The definition can be easily adapted to the case of forests, which are a sequence of trees.

The similarity score between two trees can be defined as a function of the edit distance \cite{song24}:
$$TSED(T_1, T_2) = \max\left(1-\dfrac{TED(T_1, T_2)}{\max(|T_1|, |T_2|)}, 0\right),$$ where $|T|$ is the number of nodes in the tree $T$.

Zhang and Shasha \cite{zhang89} computed TED in time complexity $$O(|T_1|\cdot |T_2|\cdot \min(depth(T_1), leaves(T_1))\cdot \min(depth(T_2), leaves(T_2))),$$ where $depth(T)$ is the depth of the tree $T$ and $leaves(T)$ is the number of leaf nodes in the tree $T$.
The algorithm is based on the concept of keyroots, which are nodes in the tree that have a left sibling, or are the root of the tree.
The keyroots are exactly the nodes that need a separate computation of the distance.

Klein \cite{klein98} came with an idea of decomposing one of the trees by heavy paths, which are paths that always follow the child with the largest subtree.
This approach leads to time complexity of $$O(|T_1|^2\cdot |T_2|\cdot \log |T_2|).$$

Pawlik and Augsten \cite{apted15,apted16} proposed the APTED algorithm (All Path Tree Edit Distance) that finds the optimal decomposition strategy for the input trees, and thus achieves the best possible time in the class of all-path algorithms.
The strategy is found in time $$O(n^2)$$ for $n=\max(|T_1|,|T_2|)$.
The whole algorithm is still limited by $O(n^3)$ time complexity, because it uses the decomposition strategy approach.

Nogler, Polak, Saha, Vassilevska Williams, Xu, and Ye \cite{nogler25} proved that TED is fine-grained equivalent to All-Pairs Shortest Paths (APSP; we need to find the shortest paths between all pairs of nodes).
With the fastest algorithm for APSP at their time, they managed to compute TED in time $$\dfrac{n^3}{2^{\Omega(\sqrt{\log n})}}.$$
This proves that TED is solvable in truly subcubic time.

Bounded TED sets an upper bound $k$ for TED, and we only compute the edit distance until it exceeds $k$.
In this setting, ideally for $k\ll n$, the distance can be computed much faster.
Das, Gilbert, Hajiaghayi, Kociumaka, Saha, and Saleh \cite{das22} proposed an algorithm that computes the bounded tree edit distance in time $$\tilde{O}(n + poly(k)).$$
The notation $\tilde{O}$ hides logarithmic factors, and $poly(k)$ denotes a polynomial function of $k$.

Fan, Lee, and Zhang \cite{xted24} analyzed the inner dependencies of subtasks when computing TED, and implemented a parallel algorithm for GPU.
They achieved up to 42 times speedup over APTED.

\subsection{Tool comparison}

We shortly describe the results of some comparisons of plagiarism detection tools that accept source code as input.
We do not provide a unified comparison of the tools, as they are often evaluated on different datasets and with different parameters, so the results are not directly comparable.

Hage, Rademaker, and van Vugt \cite{hage11} compare several tools, including JPlag, Moss, and sim, on Java student submissions.
They measure how sensitive the tools are to code modifications, and JPlag is found to be more robust to modifications than the other two tools.

Ahadi and Mathieson \cite{ahadi19} compare JPlag, Moss, and sim, on C++ student submissions.
They find that sim and Moss are better than JPlag in terms of both precision and recall.

Song, Lothritz, Tang, Bissyadé, and Klein \cite{song24} compute the correlation of several metrics, including TSED and BLEU, on Java code and shortly compare the results using different parsers, Tree-sitter \cite{treesitter} and ANTLR \cite{antlr}.
They find that the choice of parser has a significant impact on the results.
They also show that the performance of TSED is dependent on the parameters of the edit operations.

Dristi and Dwyer \cite{dristi25} focus on the difference between the functionality of the code and the look of the code, and how different metrics capture those aspects.
They define the surface similarity with standard edit distance and AST similarity with TED, and show very high correlation with CodeBLEU and moderate correlation with CrystalBLEU.

Ebrahim and Joy \cite{ebrahim26} compare CodeBLEU, CrystalBLEU, TSED, JPlag, and Dolos, on a Java dataset specifically targeting plagiarism cases.
They highlight the importance of preprocessing of the input code, and show how it can significantly boost the performance of the tools.
Dolos and CrystalBLEU outperformed the other tools.

Rahman, Khatoonabadi, and Shihab \cite{rahman26} propose a large corpus of Python classes with skeletons.
They evaluate generated code by large language models against the reference implementations in the corpus.
They measure the syntactic similarity with BLEU and structural similarity with TSED.
They find the structural alignment strong and the syntactic alignment moderate.
