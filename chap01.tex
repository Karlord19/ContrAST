\chapter{Related work}

A recent study \cite{Maisch26} analyzed plagiarism behavior of first-year computer science students at KIT (Germany) and KTH (Sweden).
They gave students solutions to problems and asked them to creatively modify them and fill in a form about their modifications.
The students were allowed to use any tools they wanted, including LLMs.
The results showed that the high-level structure of the code was often preserved, and the modified code was easily recognizable as a copy of the original code.
This study tells us that even in the current situation, the plagiarism checkers are worth using at the academic environment.

\section{Code clones}

Code clones are similar or identical code fragments that appear in different parts of a codebase.
They can be classified into different types based on their similarity.

\begin{codepair}[Type 1 clones]
\label{prg:type1clones}
\begin{lstlisting}[language=C++]
int add3(int a) {
    // sum of parameter and 3
    return a + 3;
}
\end{lstlisting}
\codepairsep
\begin{lstlisting}[language=C++]
int add3(int a) {
  return a + 3;
}
\end{lstlisting}
\end{codepair}

Type 1 clones are identical code fragments that differ only in whitespace and comments, see Program \ref{prg:type1clones}.

\begin{codepair}[Type 2 clones]
\label{prg:type2clones}
\begin{lstlisting}[language=C++]
int add3(int a) {
    // sum of parameter and 3
    return a + 3;
}
\end{lstlisting}
\codepairsep
\begin{lstlisting}[language=C++]
float add4(float x) {
  return x + 4.0f;
}
\end{lstlisting}
\end{codepair}

Type 2 clones, apart from whitespace and comments, also allow for renaming of identifiers and change in literals and types, see Program \ref{prg:type2clones}.

\begin{codepair}[Type 3 clones]
\label{prg:type3clones}
\begin{lstlisting}[language=C++]
int add3(int a) {
    // sum of parameter and 3
    return a + 3;
}
\end{lstlisting}
\codepairsep
\begin{lstlisting}[language=C++]
float add4(float x) {
  auto result = x + 4.0f;
  return result;
}
\end{lstlisting}
\end{codepair}

Type 3 clones might have some statements added, modified, or removed, but still show a significant similarity in their structure and functionality, see Program \ref{prg:type3clones}.

Type 4 clones are code fragments that perform the same functionality but are implemented differently.
An example of type 4 clones would be two different implementations of a sorting algorithm.

In the context of introductory programming courses, every solution to a given problem would be considered a type 4 clone of every other solution, as they all perform the same functionality.
We need to then focus on detecting type 1 and type 2 clones, and ideally also some level of type 3 clones, as they are more likely to be the result of copying and modifying code, rather than independently solving the same problem.

\section{Clone detection approaches}

From the input, possibly thousands of source files, a clone detector should identify and report all the code clones present in the codebase.
To achieve this, a sequence of steps is typically followed \cite{roy09}.
The detector may use only a subset of these steps, depending on the specific approach and the type of clones it aims to detect.

\begin{enumerate}
\item Preprocessing: Generated files are removed. The remaining files are fractioned into relevant units, such as functions or classes.
\item Transformation: The code is transformed into an intermediate representation.
\item Extraction: One of the following approaches is used to extract features from the code:
  \begin{itemize}
    \item Tokenization: A lexical analysis is performed, and the code is represented as a sequence of tokens.
    \item Parsing: A syntactic analysis is performed, and the code is represented as a parse tree or an abstract syntax tree (AST).
    \item Control and data flow analysis: A semantic analysis is performed, and the code is represented as a program dependence graph (PDG).
  \end{itemize}
\item Normalization: To reduce uninteresting differences between code fragments, whitespace and comments are removed, identifiers are consistently named or replaced with placeholders, and some code constructs are simplified.
\item Match detection: The units are compared and similar ones are yielded as potential clones.
\item Formatting: The original locations of the detected fragments are retrieved.
\item Filtering: Potential clones are filtered either by a human or with a heuristic, to remove false positives and retain only the true clones.
\item Aggregation: If there are many clones similar to each other, they can be grouped together to create a more compact report.
\end{enumerate}

We can then classify clone detection approaches based on the steps they use.
The level of analysis performed then impacts the types of clones that can be detected, as well as the precision and recall of the detector.

\begin{itemize}
\item Textual: The code is treated as plain text, or only some basic parsing is performed.
\item Lexical (token-based): The code is first tokenized and then normalized, and the resulting token sequences are sent for match detection.
\item Syntactic (tree-based): The code is parsed into an AST. Algorithms for tree similarity are then used. The trees can also be serialized into a token or string representation, and then token-based approaches can be applied.
\item Syntactic (metrics-based): The code is parsed into an AST, and then various metrics are computed. The resulting vectors of metrics are then compared using a similarity measure.
\item Semantic: The code is analyzed to extract its semantics. This can be done using program dependence graphs, information retrieval techniques, artificial intelligence, \dots
\end{itemize}

\section{Clone detection tools}

We shortly review some of the existing plagiarism detection tools that accept source code as input, especially those that are relevant to our work or are widely used.
We focus only on the original ideas behind the tools; many of them have evolved and now include various new approaches and features.

There exist a few parsers that can be easily integrated into a tool for tokenization or parsing.
The normalization step is often implemented as a custom solution, choosing which code constructs to simplify and how to rename identifiers.
The resulting representation can then be language-agnostic, and the same match detection algorithm instance can be used for every supported language.

Probably the most widely used detector is Moss (Measure of Software Similarity) using the winnowing algorithm \cite{moss03}.
It primarily operates on source code, but the algorithm itself is textual.
The code is first parsed and normalized based on the input format and then printed to a string representation.
All substrings of a given length are hashed, and then all windows of a certain size are created from the sequence of hashes.
From each window, the minimum hash value is selected as a fingerprint.
The fingerprints are then stored, and the detector quickly finds matching fingerprints between different documents.

JPlag \cite{jplag02} and YAP3 \cite{yap3} compare two documents at a time.
First, the code is tokenized and normalized.
Then, a string tiling algorithm is applied to the token sequences.
It tries to find the longest common substrings between the two sequences, marks them as clones, and removes them from the sequences.
This process is repeated until no more common substrings of a certain length can be found.
This approach easily detects clones with transposed code segments.

A tree is a data structure that consists of nodes connected by edges, where each node has a label and zero or more child nodes.
Tree edit distance, or TED for short, is a measure of similarity between two trees, $T_1$ and $T_2$.
It is defined as the minimum number of edit operations that transforms $T_1$ into $T_2$.
The edit operations typically include relabeling \ref{fig:ted-rename}, insertion \ref{fig:ted-insert}, and deletion \ref{fig:ted-delete}.
Insertion of a node X under a node Y means that a consecutive subset S of children of Y are reattached to X, and X is then added as a child of Y at the position of S.
Deletion of a node X means that X is removed, and its children are reattached to the parent of X at the position of X.
It can be easily seen that inserting a node into $T_1$ is equivalent to deleting a node from $T_2$, and vice versa.

In a more general setting, we can assign different cost values to each type of edit operation, and different costs to different labels.
TED is then defined as the minimum weighted number of edit operations that transforms $T_1$ into $T_2$.

The formal definition of TED is as follows \cite{zhang89}:
\begin{defn}[Tree edit distance]
Let $c$ be a distance metric that assigns a non-negative cost to each edit operation based on the labels of the nodes involved in the operation.
If $S$ is a sequence of edit operations, we define $c(S)$ as the sum of the costs of the edit operations in $S$.
Let $T_1$ and $T_2$ be two labeled trees.
The tree edit distance between $T_1$ and $T_2$ is defined as
$$d(T_1, T_2) = \min \{c(S)\},$$ where $S$ is a sequence of edit operations transforming $T_1$ into $T_2$.
\end{defn}
The definition can be easily adapted to the case of forests, which are a sequence of trees.

To compute TED, we shall not directly use the definition, as it is recursively defined and would lead to an exponential time algorithm.
Instead, we can use dynamic programming to compute the distance in polynomial time.

Tai \cite{tai79} proposed an algorithm that computes TED in $$O(|T_1|\cdot |T_2|\cdot depth(T_1)^2\cdot depth(T_2)^2)$$ time, where $|T|$ is the number of nodes in the tree $T$ and $depth(T)$ is the depth of the tree $T$.
The algorithm uses a dynamic programming approach similar to computing the edit distance between strings, but it also takes into account the hierarchical structure of the trees.

Zhang and Shasha \cite{zhang89} improved the time complexity to $$O(|T_1|\cdot |T_2|\cdot \min(depth(T_1), leaves(T_1))\cdot \min(depth(T_2), leaves(T_2))),$$ where $leaves(T)$ is the number of leaf nodes in the tree $T$.
The algorithm is based on the concept of keyroots, which are nodes in the tree that have a left sibling, or are the root of the tree.
The keyroots are exactly the nodes that need a separate computation of the distance.

Klein \cite{klein98} came with an idea of decomposing one of the trees by heavy paths, which are paths that always follow the child with the largest subtree.
This approach leads to time complexity of $$O(|T_1|^2\cdot |T_2|\cdot \log |T_2|).$$

Dulucq and Touzet \cite{dulucq03} further studied the path decompositions and relevant forests, those are the forests that need to be compared when the path decomposition is applied.
They computed $\Omega(|T|\cdot \log(|T|))$ to be the lower bound on the number of relevant forests in a tree $T$, making $$\Omega(|T_1|\cdot |T_2|\cdot \log(|T_1|)\cdot \log(|T_2|))$$ the lower bound on the number of pairs of relevant forests when computing TED between the trees $T_1$ and $T_2$.

Demaine, Mozes, Rossman, and Weimann \cite{demaine07} found a new time lower bound for all algorithms based on decomposition strategies to be $$\Omega\left(|T_1|\cdot |T_2|^2\cdot \left(1+\log\left(\dfrac{|T_1|}{|T_2|}\right)\right)\right).$$
They also proposed a new algorithm that achieves this time complexity, which is optimal among all algorithms based on decomposition strategies.

Pawlik and Augsten \cite{apted15,apted16} were able to find the optimal decomposition strategy for the input trees, and thus achieve the best possible time in the class of all-path algorithms.
The algorithm is called RTED (Robust Tree Edit Distance), and its descendant with a lower space consumption is called APTED (All Path Tree Edit Distance).
The strategy is found in time $$O(n^2)$$ for $n=\max(|T_1|,|T_2|)$.
The whole algorithm is still limited by $O(n^3)$ time complexity, because it uses the decomposition strategy approach.

Mao \cite{mao23} was the first to show that unweighted TED (with fixed cost of edit operations) can be computed in truly subcubic time, specifically in $$O(n^{2.9546})$$ time.
It is based on reducing the problem of computing TED to the problem of finding the "max-plus product of bounded-difference matrices", what is known to be solvable in truly subcubic time.

Nogler, Polak, Saha, Vassilevska Williams, Xu, and Ye \cite{nogler25} proved that TED is fine-grained equivalent to All-Pairs Shortest Paths (APSP).
With the fastest algorithm for APSP at their time, the managed to compute TED in time WHY IS THERE NO 'O' IN THERE $$\dfrac{n^3}{2^{\Omega(\sqrt{\log n})}}.$$

Bounded TED sets an upper bound $k$ for TED, and we only compute the edit distance until it exceeds $k$.
In this setting, ideally for $k\ll n$, the distance can be computed much faster.
Das, Gilbert, Hajiaghayi, Kociumaka, Saha, and Saleh \cite{das22} proposed an algorithm that computes the bounded tree edit distance in time $$\tilde{O}(n + poly(k)).$$
