\chapter{\texttt{comparatree}}\label{sec:comparatree}

\texttt{comparatree} \cite{comparatree} is a C++ library aiming to store abstract syntax trees (ASTs) of source code very efficiently with custom metadata.

We need \texttt{comparatree} to be adequately storage efficient, as we want to perform various analyses on large datasets in memory.
The permanent storage of \texttt{comparatree} instances is also important, because they store the parsed submissions.
We do not then need to store the original source code and parse it again, which saves a lot of time and space.

  \caption{Organization of files in \texttt{comparatree}.}
  \label{fig:comparatree-floors}

As shown in \autoref{fig:comparatree-floors}, the data in \texttt{comparatree} is organized into three layers in class \verb|module_flat_storage|:
\begin{itemize}
\item Module: A single file is represented by a module, which contains a structure root (global core node), a location root (global loc node), used identifier names, the absolute location of the root, and a solution ID.
\item Solution: A solution corresponds to a single submission, and contains an author ID and a batch ID.
\item Batch: A batch corresponds to a set of submissions, for example all the submissions for a single assignment collected during one day.
\end{itemize}

\section{Core storage}

The class \verb|core_tree_storage| represents all the structures of the ASTs.
By a structure we mean a subtree of the AST, which has its own kind (e.g., variable declaration or function call) and a list of children (which are also structures).

The set of possible kinds of structures is defined by type descriptors.
A type descriptor defines the kind of a structure root.
It has a unique ID number, a name, and a list of children.
Each child is either a structure reference, a placeholder for a concrete name, or a placeholder for a literal value.
The type descriptors are stored in a global registry.
Each parser can define its own type descriptors, and should create a separate library within \texttt{comparatree} for them as it allows us to have multiple type descriptors with the same IDs for different parsers without conflict.

All the concrete names used in the structures are stored in modules and are not part of the core storage.
Each unique structure is stored only once and has a unique ID starting from 0.
When we build the core storage, all the children of a structure must already be stored; this implies that the structures are stored in a bottom-up manner and the parent's ID is always greater than the IDs of its children.

Let's look closely at the deduplication using the example in \autoref{fig:comparatree-core-deduplication}.
First, we extract away the concrete names.
The compound statement then goes from \UseVerb{verb:comparatree-core-deduplication} to \verb|{ _0 = _1 + _2; _0 = _1 + _0; }|, where \verb|_0|, \verb|_1|, and \verb|_2| are different placeholders for the concrete names.
The compound statement has two children: an assignment expression \verb|a13| that receives placeholders \verb|_0, _1, _2|, and an assignment expression \verb|a14| that receives placeholders \verb|_0, _1|.
The assignment expression \verb|a13| has two children: a variable reference \verb|a9| that receives placeholder \verb|_0|, and a binary operator \verb|a11| that receives placeholders \verb|_1, _2|.
The binary operator \verb|a11| has two children: both are variable references \verb|a9|, and one of them receives placeholder \verb|_0| while the other receives placeholder \verb|_1|.

For reconstruction of the original code from the example in \autoref{fig:comparatree-core-deduplication} with the concrete names, each structure receives the concrete names for its placeholders.
The compound statement receives names \verb|a, b, c|.
It prints \verb|{|, then prints the first child \verb|a13| with names \verb|a, b, c|, then \verb|; |, then the second child \verb|a14| with names \verb|a, b|, and finally \verb|}|.
The assignment expression \verb|a13| receives names \verb|a, b, c|, prints the first child \verb|a9| with name \verb|a|, then prints \verb| = |, and finally prints the second child \verb|a11| with names \verb|b, c|.
The binary operator \verb|a11| receives names \verb|b, c|, prints the first child \verb|a9| with name \verb|b|, then prints \verb| + |, and finally prints the second child \verb|a9| with name \verb|c|.
The variable reference \verb|a9| just prints the name it receives.

See how the child structures do not have a reference to their parent structure, so that they can be shared by multiple parent structures and used in different contexts.
In the example in \autoref{fig:comparatree-core-deduplication}, the binary operator \verb|a11| is shared by both assignment expressions \verb|a13| and \verb|a14|, once as \verb|b + c| and once as \verb|b + a|.

Each module has a global core node that points to the structure of the whole file, and a list of concrete names that are used in the file.
The concrete names are stored in the order of their first occurrence in the file, so we can directly use it to reconstruct the original code by sending this list of names to the global core node.

\section{Location storage}

The class \verb|loc_tree_storage| represents the locations of the structures in the source code.
It is completely separate from the core storage, so that the same structure can be used in different locations and contexts.

We distinguish these types of locations:
\begin{itemize}
\item Absolute location: A concrete location in a file, represented by a file ID, a line number start and end, a column number start and end, and a character offset start and end.
\item Size location: A location span, represented by a length in lines, columns, and characters. Written as \verb|<lines, columns, chars>|.
\item Relative location: A location relative to another one, represented by a line and a column number offset. Written as \verb|{line_offset, column_offset}|. The offset is added (or subtracted if negative) to a reference location to get the resulting location.
\item Location node: A node in the location storage, represented by a size location and a list of children. Each child is represented as a relative location and a location node ID.
\end{itemize}

The location storage stores only the location nodes and is built in a bottom-up manner.
Each unique location node is stored only once and has a unique ID starting from 0.

\begin{figure}[ht]
  \centering
  \includegraphics[width=0.6\textwidth]{img/comparatree-loc-deduplication.eps}
  \caption[The deduplication in location storage.]{The deduplication in location storage of\\\protect\parbox[b]{0.42\linewidth}{\ttfamily\raggedright\textbraceleft\\\ \ a = b + c;\\\ \ a = b + a;\\\textbraceright}}
  \label{fig:comparatree-loc-deduplication}
\end{figure}

In \autoref{fig:comparatree-loc-deduplication}, we can see the deduplication in location storage corresponding to the same code as in \autoref{fig:comparatree-core-deduplication}.
The compound statement corresponds to the node \verb|L9| and has two children \verb|L8|.
The first child is shifted by \verb|{1,2}|, meaning that it starts \verb|1| line and \verb|2| columns after the start of the compound statement.
Both assignment expressions correspond to the same node \verb|L8|, but beware that their locations are different because of the different relative location from the compound statement.
The node \verb|L8| has a child \verb|L5| that is not shifted, meaning that it starts at the same location as the assignment expression, and a child \verb|L6| that is shifted by \verb|4| columns.
The binary operator in both assignments corresponds to the node \verb|L6|.
It has one child \verb|L5| that is not shifted, and another child \verb|L5| that is shifted by \verb|4| columns.
Every variable reference in this example corresponds to the same node \verb|L5|.

Beware that if one of the assignments in \autoref{fig:comparatree-loc-deduplication} was written with different spaces in between, for example \verb|a=b + c;|, it would have a different location node than the other assignment.
In this example, the \verb|b + c| part is written as before, so it would still correspond to the same node \verb|L6|.

Each module has an absolute location corresponding to the global loc node.
We can reconstruct the absolute location of any structure in the core storage.
We start with the absolute location of the module from the global core node and the global loc node.
The sequence of children of a location node corresponds to the sequence of children of the core node, so we can easily descend in both the location storage and the core storage at the same time.
We apply the relative location along the way.

\section{Statistics}

To prove how storage efficient \texttt{comparatree} is, we compared the original code size with the size of a corresponding \texttt{comparatree} instance.
The tests were performed with \texttt{atc} (details in \autoref{sec:atc}) on C++ submissions.
The size depends heavily on the parser and the amount of information we want to capture in the AST, but we currently have only \texttt{atc}.

Based on the deduplication in both core and location storage, the size also depends on the amount of repetition in the code.
One student can submit the same (or very similar) code multiple times, which directly leads to more deduplication and smaller size of the \texttt{comparatree} instance.
The tests were performed on actual student submissions in \texttt{ReCodEx} during a certain period of time, so they reflect the real-world usage of \texttt{comparatree}.
